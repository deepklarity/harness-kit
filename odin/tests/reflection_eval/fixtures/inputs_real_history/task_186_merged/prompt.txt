## Design — what landed

### 1. The hook: dispatch from REVIEW → TESTING

`_advance_task_to_testing` (in `tasks/dag_executor.py`) is the single
TESTING-entrance point.  After the existing REVIEW → TESTING transition
lands, it now:

1. Checks `board.metadata["auto_promote_enabled"]` (default ON) and
   that the task has a spec + branch (no worktree ⇒ nothing to gate).
2. If eligible, dispatches `auto_promote_testing_task.delay(task.id)`.
3. Wraps the dispatch in try/except — a broker outage or transient
   import error CANNOT regress the TESTING transition or strand the
   auto-promote silently.  The log line + the operator's existing
   TESTING hand-off are the only signals on dispatch failure.

### 2. The celery body: `auto_promote_testing_task`

Lives in `tasks/auto_promote.py`.  The body:

1. Re-fetches the task and short-circuits on missing / non-TESTING.
2. Re-checks the board flag (covers the case where the flag was
   flipped between dispatch and execution).
3. Runs the gate via `_run_odin_promote_check` (subprocess
   `odin promote-check <task_id>`) — reuses the operator's CLI so
   any future gate change is automatically inherited.  Parses the
   `### RECOMMEND PROMOTE` / `### HOLD:` headline line.
4. On **promote** → `_apply_auto_promotion`:
   - Refresh + status guard (never regress a non-TESTING task).
   - `task.status = DONE; task.save(update_fields=[...])`.
   - `TaskHistory(changed_by="system+auto-promote@taskit")` — the
     system identity that distinguishes auto-promote from a
     manual operator flip in the audit trail.
   - `TaskComment` status update linking the timeline to the
     gate's `promotion_report` comment id (`see #9001 for the
     full evidence`).
   - Metadata stamp: `auto_promote_recommendation`, `auto_promote_at`,
     `auto_promote_actor`, `auto_promote_promotion_report_comment_id`.
   - `_cleanup_done_task_worktree(task)` — the shared helper the
     API-DONE and spec-finalize paths already use; branch is
     preserved, disk is reclaimed.
5. On **hold** → `_stamp_hold`:
   - Refresh + status guard.
   - Metadata stamp (recommendation + gaps as a `;`-joined string).
   - No status change, no comment — the gate's own
     `promotion_report` comment already names the gap, the
     operator's pre-wave-4 flow applies.
6. On **error** → `_stamp_gate_error`:
   - Metadata stamp (error string + timestamp).
   - Single status comment: `Auto-promote gate crashed: <type>: <msg>.
     Task stays in TESTING — operator action required.`
   - No status change — a transient subprocess failure is NEVER
     a reason to move the task.

### 3. The board-level off switch

`Board.metadata` is a new `JSONField` (migration `0049_board_metadata`).
A board opts out by setting `metadata["auto_promote_enabled"] = False`
(JSON boolean false; string `"false"` is intentionally truthy in
Python and is therefore NOT honored — pinned by the
`test_flag_truthy_string_disables_actually_no_it_enables` test as the
documented operator contract).

`_board_allows_auto_promote(board)` is the public gate-check helper;
`_should_auto_promote(task)` adds the spec/branch preconditions on top.

## Why a subprocess gate (not a Python call)

`odin.promote_check.build_promotion_report` is pure data-in / data-out
and importable from the backend (one-way coupling: taskit-backend MAY
import from odin).  We could have called it directly and skipped the
`scripts/verify.sh` subprocess.  We chose the subprocess anyway:

- **Single source of truth.**  Whatever the operator runs by hand
  (`odin promote-check`) is exactly what the auto-promote runs.  No
  drift between the two surfaces.  Any future gate change is
  automatically inherited.
- **Testable end-to-end.**  The `odin.promote_check` suite stays the
  single test target for the gate logic; the backend only tests the
  apply step (the new shape, the new error paths).
- **Crash isolation.**  A bug in the gate's subprocess can never
  poison the celery worker process; the worst case is a single
  missing auto-promote with an error comment posted.
