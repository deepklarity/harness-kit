# Task 195 — Honest `verify.sh frontend` in a fresh worktree

## Problem

In a fresh worktree (no `node_modules`), `scripts/verify.sh frontend` ran
`npm run test:run`, which died in **0.11s** with:

```
sh: 1: vitest: not found
```

`verify.sh` recorded that as `frontend|FAIL` and exited non-zero.
`odin promote-check` then reported:

```
HOLD: suite frontend FAILED:  (critical)
```

That is a **fake critical-suite HOLD** — there was no test failure, no code
regression, just a missing toolchain. Auto-promotion (which just shipped)
treated every clean task in a fresh worktree as a code failure, stalling
promotion until a human checked by hand. The task brief: *"Auto-promotion
just shipped, and if the gate keeps crying wolf every clean task will stall
in exactly the way auto-promotion was built to end."*

Reproduction (this worktree, before the fix):

```
$ time sh scripts/verify.sh frontend
running frontend  ... frontend FAIL (0.11s)
verify.sh: RED — at least one suite failed
=== EXIT 1 ===                                   # ~0.13s wall clock
```

Raw failure output (`.verify-logs/frontend.log`):

```
> orch-dash@0.0.0 test:run
> vitest run

sh: 1: vitest: not found
```

## Fix — distinct `ENV_MISSING` category (cheapest, most truthful)

Three options were on the table:

1. `npm ci` against a shared host npm cache inside `verify.sh`
2. A shared `node_modules` strategy (symlink/bind-mount)
3. A distinct `ENV_MISSING` result that promote-check treats as
   "provision and retry", not HOLD-as-code-failure

**Picked option 3.** One-sentence justification: it is the cheapest and
most truthful fix — it keeps `verify.sh` focused on *running* tests (no
network dependency, no npm flakiness baked into the gate), makes the report
honest about *why* the suite didn't run, and lets the existing
auto-promote / CI flow decide how to provision without embedding npm
provisioning into the test runner. The fake HOLD becomes impossible because
the gate no longer conflates "toolchain not installed" with "tests ran and
failed" — two failures with completely different fixes.

This also aligns with the repo's existing failure taxonomy:
`taskit-backend/tasks/failure_tagger.py` already has an `env_missing` class
with signatures for `"command not found"` / `"not found on path"`. This
change extends the same concept to the verify gate.

## Files changed

### 1. `scripts/verify.sh` — emit `ENV_MISSING` when the toolchain is missing

`run_suite` now classifies a non-zero exit as `ENV_MISSING` (instead of
`FAIL`) when **both** of these hold:

1. **No test counts were parsed** — `summary` is empty. A real test
   failure *always* emits a summary line (vitest: `Test Files N failed`,
   pytest: `N failed in Xs`, Django: `FAILED (failures=N)`). An empty
   summary means the tool never produced output.
2. **The log contains a shell exec-failure pattern** — `command not found`,
   `: not found`, or `No such file or directory`. These are the OS-level
   errno strings from a failed `exec()`, not test-framework messages.

The combination is conservative: a real test failure cannot trigger this
branch because it always produces a summary line. A toolchain-missing
failure always produces the "not found" pattern with no summary.

The gate decision and final message were also updated to be honest:
`ENV_MISSING` counts toward a non-zero exit (a suite that couldn't run is
not a pass), but the summary message names the category distinctly:

```
verify.sh: RED — 1 ENV_MISSING (provision and retry)
```

vs. the old conflated message:

```
verify.sh: RED — at least one suite failed
```

### 2. `odin/src/odin/promote_check.py` — recognize `ENV_MISSING`, name the gap

- **`SuiteRow`** gained an `env_missing: bool` field. `from_result` sets
  it when `verdict == "ENV_MISSING"` (distinct from `FAIL`).
- **`build_promotion_report`** checks `row.env_missing` *before* the
  critical/known-red branches. An env-missing suite produces the gap:

  ```
  environment missing: suite frontend could not run (toolchain not installed; provision and retry)
  ```

  …never the old `suite frontend FAILED: (critical)`. Crucially,
  env-missing is **never silently tolerated** — even a known-red suite
  (snapshots) reports an env gap when its toolchain is missing, because
  KNOWN_RED tolerance is for *test* failures we accept, not for "the suite
  didn't run at all".
- **`render_report`** shows an `ENV` marker (distinct from `FAIL`) so an
  operator scanning the report sees at a glance this is an environment
  gap, not a code regression.
- **`render_attachment`** carries `env_missing: True` per suite so
  downstream consumers (auto-promote, the board UI) can branch on it
  without re-parsing the rendered text.

### 3. `odin/tests/mock/test_promote_check.py` — 10 new tests (`TestEnvMissingSuite`)

Written first, confirmed failing before the fix (9/10 failed; the 10th —
`test_real_failure_still_uses_critical_gap` — passed as the regression
guard). After the fix, all 10 pass. Coverage:

- `ENV_MISSING` verdict → `SuiteRow(passed=False, env_missing=True)`
- `PASS` / `FAIL` verdicts → `env_missing=False` (no misclassification)
- `parse_verify_results` recognizes `ENV_MISSING` in `_results.txt`
- Critical suite env-missing → HOLD with named environment gap (not
  `FAILED`, not `(critical)`)
- Gap text names the suite + the action (`provision` / `retry`)
- Real `FAIL` on critical suite → still `(critical)` gap (regression guard)
- Known-red suite env-missing → still named (never silently tolerated)
- Rendered body shows `ENV` marker, not `FAIL`
- Structured attachment carries `env_missing` flag
