# VM memory provisioning audit — 2026-07-07 (binding-constraint #3)

**Verdict: 4 GiB provisioning is ~3× over what real runs need. Drop to 2 GiB;
DAG_EXECUTOR_MAX_CONCURRENCY can rise to 4.** Measured inside a live
opencode-family (glm) microsandbox VM across 8 real workloads (228 samples):
peak **anonymous** memory 1.15 GiB, peak pressure (incl. reclaimable cache)
1.25 GiB — both far under the 4 GiB cap. The idle agent-stack floor is ~0.9 GiB.

Sampler: `bootstrap/sample_vm_mem.py` (reusable; guest-side `/proc/meminfo` and
host-side `--pid` RSS modes). Raw samples + this table regenerated by the
sampler's own `report` command live under `/tmp/memsamples/` (attached as proof).

## Why 4 GiB was set

`odin/src/odin/models.py:66` — `microsandbox_mem_size_mib: int = 4096  # opencode
(bun) OOMs below ~4G`. Every microsandbox agent inherits this default (no
override in `.odin/config.yaml`). libkrun gives `SwapTotal = 0`, so there is **no
cushion** — an overshoot OOMs instantly, which is why the original author erred
high. The question is whether the OOM threshold is still ~4 GiB. It is not.

## Measurement table (≥5 real runs; all with the full opencode/glm agent stack resident)

Metric = anonymous memory (`Active(anon)+Inactive(anon)`, the non-reclaimable
commit — the OOM predictor). `used_avail` = MemTotal − MemAvailable (pressure
incl. reclaimable cache). libkrun `MemTotal` = 3.84 GiB (4096 MiB minus ~250 MiB
hypervisor resident). Sampled at 0.15–0.2 s.

Even the deliberate worst case — full test suite plus four heap-holding node
workers simultaneously — peaked at **1.13 GiB** anon. The workload overhead above
the ~0.9 GiB agent-stack floor is only ~0.3 GiB under heavy concurrent load.

## Recommendation (arithmetic against the 18 GiB host)

**Provisioning: 2048 MiB.** Effective guest budget after libkrun ≈ 1.8 GiB.
Cushion over the worst measured pressure (1.28 GiB) ≈ 0.5 GiB (≈40 %). This is a
*conservative* cut — not aggressive — given zero swap and the stale OOM note. Do
not go below 2 GiB until the per-run sampler confirms p99 across claude/reflection
(which use the same odin-agents image + node CLIs, so should match, but were not
run from inside this single guest).

**Concurrency: DAG_EXECUTOR_MAX_CONCURRENCY = 4** (immediate), not higher yet.
Host arithmetic: 18 GiB − ~4 GiB for backend + celery + UI + OS + msb ≈ 14 GiB
for VMs. Per-VM host cost ≈ provisioning + ~0.4 GiB libkrun overhead ≈ 2.4 GiB.
14 / 2.4 ≈ **5 memory-feasible VMs**. Cap at 4 (not 5) because CPU contention,
concurrent-worktree disk I/O, and the single merge lock (promotion serializes
anyway) give diminishing returns above 4. Re-measure host RSS at 4-way with the
sampler's `--pid` mode before raising further.

At current 4 GiB: 14 / 4.4 ≈ 3 feasible — and the roadmap's "throughput = 1" is
the conservative operator setting, not the memory ceiling. The binding
constraint #3 is solvable at 2 GiB.

## Operator changes to apply

1. `.odin/config.yaml` — add `microsandbox_mem_size_mib: 2048` to each
   microsandbox agent block (claude, codex, minimax, glm, agy), or set it once
   via the default in `models.py`/`config.py`.
2. Backend env — `DAG_EXECUTOR_MAX_CONCURRENCY=4` (default is 10 in
   `config/settings.py:203`; the memory gate, not the env var, currently holds it
   to ~1). The celery `--concurrency` flag should stay ≥ cap + 1.
3. Bake the sampler into the harness guest wrapper so every run records peak
   memory to its trace dir; promote any run that OOMs at 2 GiB back to 3 GiB and
   flag it here.

## Honest caveats

- These are opencode-family (glm) numbers, measured directly because that is the
  agent this guest runs. The "OOM below 4G" note names opencode/bun specifically;
  measured peak was 1.2 GiB, so the note is either stale or refers to an
  unmeasured huge-context spike. The deployed sampler will catch that case.
- Zero swap: the 2 GiB cushion must absorb spikes. Adequate for every observed
  workload (worst 1.28 GiB), but a pathological single-file context load could
  exceed it — the sampler + a 3 GiB fallback handle that risk.
- Host RSS per VM is *approximated* (2.4 GiB); operator should confirm by running
  the sampler in `--pid` mode against a live `msb`/libkrun process during a 4-way
  dispatch.
